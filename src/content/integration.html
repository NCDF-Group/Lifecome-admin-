Professional Portal → Patient Health Records

The professional portal is the authoring workspace. The patient app is the patient-facing view of approved information in the same clinical record. Do not build two independent record databases.

Professional portal · 56-screen board · API contract · Screen register · Verification report

Demonstration boundary: all records and professional identities are fictional. There is no real authentication, clinical database, e-prescribing, laboratory, pharmacy, video or payment integration. Client-side permissions and audit logs demonstrate intended behaviour; they are not production security controls.

What the two-app demonstration does

  1. Choose a professional role and patient in the portal.
  2. Save observations; sign a note and release its patient summary; authorise a fictional prescription; review and release a result; or sign a care/wellbeing record.
  3. Open Patient app preview → Open existing patient app. The existing patient demo receives the selected patient’s released record and displays it under Health Records → Professional record updates.
  4. Keep the linked patient window open. Further professional updates send a fresh released snapshot for that same patient. Draft and unreleased content are excluded.
  5. If the browser blocks the window connection, export the released demo JSON and import it on the patient app’s Professional updates screen. The same-origin companion patient view also reflects releases.

The browser bridge uses exact-origin checks and fictional patient IDs, not an authenticated clinical connection. It only demonstrates the information flow. It is not suitable for real patient information. The separate companion view uses local browser storage; it is not a cloud or multi-device record.

Required production architecture

Both applications must use a shared clinical API and canonical patient identifier. The professional portal writes authorised, versioned updates; the patient app reads a patient-scoped released projection. Store signed originals and amendments separately. API services own access, workflow transitions, audit and release decisions.

Record Professional action Patient-app behaviour
Observations Record measured values, units, time, author and context Display approved observations against the same patient
Consultation Draft → review → sign → release summary Show the released summary; full notes only through an explicitly approved release policy
Amendment Add signed addendum; preserve original Re-release relevant changes and preserve provenance
Prescription Draft → safety review → authorised signature → transmission Distinguish prescribed, sent, acknowledged, dispensed and cancelled states
Laboratory result Receive → match → review → assign action → release Show reviewed explanation and next action; withhold unreleased results
Referral Draft → approve → send → track acknowledgement and outcome Show the referral and appropriate status
Care / wellbeing Sign visit record or agreed plan Show agreed patient-facing summary, excluding staff-only concerns

Identity and access

  • Canonical patient ID, organisation ID, encounter ID and record ID on every resource. Do not match patients by name or email alone.
  • Verified professional identity, registration and role; separately verified prescribing privileges. Include patient assignment and purpose of access.
  • Patients can read only their own released record; proxy and carer access requires separate authority, scope and audit.
  • Server-side authorisation on every read, write, search, export and notification. Default-deny sensitive fields and restrict administrative roles.
  • Authentication, multi-factor protection for staff, session controls, encryption, retention rules, access reviews and incident response require production implementation.

Write and release contract

The supplied OpenAPI file is a proposed implementation contract, not a running API. Record writes include a version and an idempotency key. Reject stale writes with 409 Conflict; never silently overwrite a newer clinical record. Validate clinical status transitions server-side. Signed content is immutable; create a linked addendum for corrections. Release records only after identity, authority and release-policy checks.

A patient-record projection must carry the patient ID, source record ID, resource type, version, clinical status, visibility, author, signed/released timestamps and patient-readable content. The supplied sample contract illustrates these fields; agree the exact clinical resource model with the chosen clinical-system and laboratory providers. A FHIR mapping may be appropriate but this demo does not claim FHIR conformance.

Delivery, reconciliation and failure handling

  • Commit clinical writes and an outbox event atomically. Events should carry record references and versions; do not distribute full clinical payloads unnecessarily.
  • Publish record-release, amendment and cancellation events; update the patient projection idempotently. Polling or server push may refresh the app.
  • Record event ID, retry count, failure status and reconciliation outcome. Retry safely; route exhausted retries to a monitored queue.
  • The patient app must show an update timestamp and meaningful failure/loading states. Never imply delivery or patient reading simply because a record was released.
  • Deduplicate laboratory messages, verify patient/sample/order linkage and quarantine unmatched reports. Ensure every actionable result has an owner and due date.
  • Prescribing and pharmacy transmission require separate signed-message integration, acknowledgement and cancellation handling. The current fictional medicine must never be mapped to a dispensable product.
  • Neutral notifications should direct the patient to the secure app. Avoid sensitive result details in email/SMS or lock-screen text.

Minimum acceptance tests for live integration

  1. A patient cannot access another patient’s records by changing any identifier.
  2. Reception cannot access clinical content; non-prescribers cannot authorise prescriptions.
  3. Draft notes and unreviewed/unreleased results never appear in patient APIs, exports or notifications.
  4. Signed records resist overwrite; addenda preserve the original, author and chronology.
  5. Duplicate events do not create duplicate entries; concurrent edits produce an explicit conflict.
  6. Cancelled prescriptions and amended results propagate without losing history.
  7. Failed lab matching, pharmacy transmission or patient projection updates remain visible to responsible staff.
  8. Consent limitations, restricted records, safeguarding decisions and proxy access are applied consistently.
  9. Patient-app content matches the released source version, including after offline/reconnect scenarios.

What is still needed before clinical launch

Confirm the selected clinical record system, prescribing/pharmacy and laboratory partners, provider service scope, clinical policies, information-governance documentation, clinical safety assessment, approved templates and terminology, role permissions, release rules and end-to-end acceptance testing. Do not use this demonstration with real patient records or as evidence that regulatory or clinical requirements have been met.
